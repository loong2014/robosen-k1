# K-ONE 蓝牙控制与业务逻辑分析

分析对象：`com.robosen.K1app`，版本 `4.75.20260601`，versionCode `75`。
分析日期：2026-09-19。原始 APK 未修改。三包 SHA-256 见 [apk_inventory.json](apk_inventory.json)。

## 1. 结论与证据范围

已恢复 K1/K1AI 设备的 BLE 接入参数、旧协议组包算法、指令枚举、若干业务载荷和接收事件分发逻辑。已提供可运行的离线编解码参考代码。

| 项目 | 结论 | 验证范围 |
|---|---|---|
| 通信方式 | BLE GATT，Android Shatalmic 插件 | Java 实现 + Unity 调用路径 |
| 设备名 | `K1-`、`K1AI-` 是设备类型匹配前缀 | 原生取值函数 + IsOldProtocolDev |
| Service | `0000ffe0-0000-1000-8000-00805f9b34fb` | 原生字符串引用 |
| Characteristic | `0000ffe1-0000-1000-8000-00805f9b34fb`，用于写入和订阅 | 原生设备类型映射 |
| 写入方式 | `withResponse=false`，Android write type 1 | BTDevice.SendData + Java |
| MTU | 应用请求 512；实际值以协商回调为准 | 连接特征发现回调 |
| K1 协议 | `FF FF LEN CMD PAYLOAD SUM8` | 原生组包函数；96 组机器码对照验证 |
| 应用层 ID | BLECommand.ID 是本地递增值，不写入旧协议帧 | 构造函数与组包函数 |
| 加密/握手 | 已确认路径直接组帧，无应用层加密；发送空载荷 0x0B 握手 | 不代表所有功能/固件都无额外要求 |
| 指令 | 59 个枚举项（含 -1、0xFF 等特殊项） | 元数据直接恢复，非全部已验证可执行功能 |
| 调用点 | 导出 87 处直接调用 BTDevice.SendData 的位置 | 包含条件分支、协程与重复功能路径 |

**没有连接机器人或发送任何控制指令，没有取得实际空口/运行抓包。** 下文“已确认”指 APK 静态逻辑或明确写出的机器码离线验证，不等于固件行为已验证。

## 3. 调用链

发送：

```text
界面 / 协程 / 动作编辑器
  → BTDevice.SendData(commandType, datas)
  → BTDeviceType.IsOldProtocolDev(BT_name)
  → BLEProtocol.TransferCommandToData        [K1/K1AI 路径]
  → BluetoothLEHardwareInterface.WriteCharacteristic(..., false, ...)
  → UnityBluetoothLE.androidWriteCharacteristic
  → WriteCharactersticBytes
  → BluetoothGatt.writeCharacteristic
```

接收：

```text
BluetoothGattCallback.onCharacteristicChanged
  → Java 将字节转 Base64，UnitySendMessage("BluetoothLEReceiver", "OnBluetoothMessage", ...)
  → BluetoothDeviceScript / BluetoothLEHardwareInterface 的订阅回调
  → Unity2BTCommandControl.ResultData
  → BTDevice.DataResult（按设备过滤，加入 CommandsBuffer）
  → BLEProtocol.GetCommandsFormList
  → BTDevice.CommandInvoke
  → RobotStates / ReciveHandShake / WriteDataToFileSuccess 等事件
```

这里的 Base64 是 Java→Unity 桥接编码，不是机器人无线协议编码；二次开发直接使用原始字节即可。

## 4. 设备选择、连接和 GATT

`BTDeviceType.get_UseOldProtocol_List` (`0x2040CA4`) 包含：

```text
T9- K1- K1AI- OP-M- CXGFN- XGZGFN- CTGEN- CXGEN- XGZGEN- GSEG-
```

`IsOldProtocolDev` (`0x203E4D0`) 对设备名逐项做前缀匹配。K1/K1AI 命中旧协议；这张列表是协议选择依据，不应当直接视为当前界面扫描结果的完整过滤条件。

UUID 原始方法：

| 方法 | VA | 实际值 |
|---|---|---|
| get_Service_F0 | `0x20418C0` | FFE0 |
| get_Characteristic_F1 | `0x204190C` | FFE1 |
| get_Service_C0 | `0x2041958` | 本版本同样为 FFE0 |
| get_Characteristic_C1 | `0x20419A4` | 本版本同样为 FFE1 |

不要由 `F0/F1/C0/C1` 方法名称推断 UUID；必须使用实际字符串。`GetDevSubscribeInfo` 与 `GetDevWritInfo` 负责选择对应服务/特征。

已确认的顺序：

1. 扫描得到地址及名称，创建 BTDevice。
2. Java 使用 `connectGatt(context, false, callback, 2)`，即不启用 autoConnect、使用 LE transport。
3. 连接回调中 `discoverServices()`；发现服务后请求连接优先级并上报特征。
4. Unity 特征匹配后请求 MTU `0x200`（512），见 `<ConnectDev>b__2`，VA `0x2042524`，关键指令 `0x20427DC`。
5. MTU 成功回调后进入 `SetBleNotifition`，订阅 FFE1。
6. Java 开启本地 notification，再写 CCCD `00002902-0000-1000-8000-00805f9b34fb`：优先 Notification 属性，否则 Indication。
7. CCCD 写成功回调后，Unity 调用 `BTDevice.OnConnect`。业务连接流程发送 0x0B 握手，并继续获取设备信息。

应用“业务可用”的时点晚于 Android GATT connected；不要只收到 connected 就发送所有业务命令。

MTU 成功后插件保存 `mtu - 3` 作为分片载荷上限。其默认 `_mtu=0` 时直接尝试整段写入，并不会自动使用 20 字节。连续片段依赖 `onCharacteristicWrite` 推进；发送状态在插件实例中共享，每次新写都会重置状态。二次开发建议使用串行写队列，按实际 MTU 分片；GATT 写完成与机器人业务 ACK 必须分开处理。

## 5. K1 旧协议精确定义

令载荷长度为 N：

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| 0 | 2 | `FF FF` |
| 2 | 1 | `LEN = N + 2`，包含 CMD 与 SUM |
| 3 | 1 | CMD |
| 4 | N | PAYLOAD |
| 4+N | 1 | `SUM = (LEN + CMD + sum(PAYLOAD)) & 0xFF` |

总帧长 `N + 5 = LEN + 3`。校验不包括两个 FF。是累加和，不是反码，也不是 CRC16。

原生证据：

- [BLEProtocol.TransferCommandToData](../native/BLEProtocol.TransferCommandToData.2040048.asm)，VA `0x2040048`。
- [BLEProtocol.GetSum](../native/BLEProtocol.GetSum.204377c.asm)，VA `0x204377C`，从数组索引 2 累加到末尾。
- [BTDevice.SendData](../native/BTDevice.SendData.2031bec.asm)，VA `0x2031BEC`。

特殊情况：`SendData(0xFF, data)` 直接写入 data，跳过组帧；0xFF 在这个发送入口不是普通包内指令。`FailureCommand=-1` 是本地解析失败标记，不能当作发送命令。旧协议只容纳至多 253 字节载荷；原 APK 对长度采用 byte 截断，参考实现主动拒绝超长输入。

参考代码：[kone_protocol.py](../reference/kone_protocol.py)。StreamDecoder 处理跨通知分片、一次通知含多个帧、前导噪声与错误校验，断线应清空缓存。错误恢复更严格，未照抄原 APK 所有异常处理行为。

注意：方向名称来源于枚举和摇杆调用；机器人实际是平移、转身还是特定姿态下动作，要结合固件和当前模式确认。音量 value 的单字节布局已确认，但不能仅由该发送函数断言所有固件都接受 0–100。

摇杆 `FixedUpdate` 使用约 ±0.5 阈值判断方向。`JoySendStop` 启动后发送 5 次 0x0C，每次等待约 0.2 秒（float 常量文件偏移 `0xBAA850`）。这说明“松开摇杆”的行为有重发逻辑，不能只照搬方向枚举。

## 7. 接收字段和事件

`BTDevice.CommandInvoke` VA `0x203EE28` 按命令码分发：

| 命令 | 回调/处理 |
|---|---|
| 0x0B | ReciveHandShake；取 payload[0]，空载荷走默认值 0 |
| 0x0F | 构造 RobotStateMSG 并触发 RobotStates |
| 0x0A | RobotTransformDone |
| 0x16 | FolderActionNamesRecive |
| 0x17 | ActionProgress |
| 0x18 | FolderAudioNamesRecive |
| 0xDC | CreateNewActionFileDone |
| 0xE3 | WriteDataToFileSuccess |
| 0xE6 | InEditorStart |
| 0xE8 | MoveJointDone，读取单字节结果 |
| 0xE9 | RobotUpJointData，继续交给业务层 |
| 0xF1 | RobotSN_DateRecive |
| 0xF5 | RobotOnUSBModeRecive |
| 0xF7 | RobotVersionRecive |
| 0xF8 | RobotVersionDateRecive |
| 0xFA | ActionNameReciveDone（与发送侧“关机”同码，方向/上下文很重要） |
| 0xFF | NoTypeCommand |

状态 payload 的字节布局由 [RobotStateMSG 构造函数](../native/RobotStateMSG..ctor.203f68c.asm) 确认：

| payload 偏移 | 字段 | 已知程度 |
|---:|---|---|
| 0 | 本构造函数未赋给 pattern 字段 | 保留原始值，不擅自命名其含义 |
| 1 | Battery | 字节值；物理量范围仍需实机核对 |
| 2 | Volume | 字节值 |
| 3 | PlayProgress | 字节值 |
| 4 | Gyros | 字节值；UI 用于相关开关 |
| 5 | Speed | 字节值 |
| 6 | Charg | 字节值；具体枚举未确认 |
| 7 | AutoOff | 字节值；具体固件含义待验证 |

构造函数会复制最多 8 个字节到 int[8]，短数据剩余位置为 0，超出部分忽略。参考 `parse_state()` 保留这一行为，并额外暴露 raw0。

## 8. 动作文件传输

已确认路径：`RobotActionInterfaceScript.<DownActionFile2Robot>d__65.MoveNext`，VA `0x20DC95C`。

1. 路径/文件名使用 `Encoding.GetEncoding("GB18030")` 编码。
2. 订阅 `CreateNewActionFileDone`（0xDC）和 `WriteDataToFileSuccess`（0xE3）。
3. 发送 0xDC + 编码后的路径，等待回调或等待条件超时。
4. 按 65 字节（常量 0x41）切分文件内容，最后一块可不足 65 字节。
5. 每块发送 0xE3 + 数据，等待设备业务确认，再推进。
6. 此循环有确认前重新发送的路径，不能替换成不等待 ACK 的高速连续写入。
7. 收尾移除事件订阅。本方法中未观察到独立发送 0xDE；虽然枚举中存在该值，不能据此给这条流程额外添加“写完”命令。

65 字节是本业务文件分块大小，不是 ATT MTU。组帧后是 70 字节，之后仍可能再被底层 BLE 插件按实际 MTU 拆分。

尚未完整还原：动作文件内部结构、关节角度单位/边界、24 个逻辑关节与物理舵机映射、全部路径编码约束、重试退出条件及不同动作编辑器之间的差异。对应原生代码已经导出，可以继续追踪，而不需要重新解包。

## 9. BLEProtocol2 的边界

应用还保留 `BLEProtocol2`（带 16 位指令及 CRC 相关方法），但 K1/K1AI 的正常 SendData 分支命中旧协议。其函数/签名和 ARM64 已导出，本报告不把其中常量混入 K1 旧协议，也未给出未经核对的 CRC 参数或帧格式。若目标设备广播名不同，应先确认协议选择路径。

## 10. 验证与使用

```bash
# 在项目根目录；只生成字节，不连接任何设备
python3 analysis/reference/kone_protocol.py --command 0x0b
python3 analysis/reference/kone_protocol.py --command 0x0d --payload 32
python3 analysis/reference/kone_protocol.py --decode 'FF FF 02 0F 11'

# 离线原始 ARM64 组包对照，依赖项目内 Python 虚拟环境
analysis/tools/venv/bin/python analysis/scripts/verify_native_codec.py
```

[验证记录](codec_verification.json)：96 组不同命令/载荷，包括 0、1、2、8、16、20、128、252、253 字节，与原始 `BLEProtocol.TransferCommandToData` 和 `GetSum` 机器码执行结果一致。模拟器只替代了托管内存分配、元数据初始化和 List 操作；协议组包与校验指令由原始机器码执行。另验证了 31 种分片步长、错误校验重同步、raw passthrough 和超长拒绝。

尚未在机器人上确认：发现到的真实 GATT 属性、协商后 MTU、握手应答值、各物理动作、所有固件型号兼容性。没有把“Python round-trip 成功”当作设备协议验证。

## 11. 补齐实机数据的方法

已准备可选 [trace_ble.js](../reference/trace_ble.js)，对本 APK 的 Java 蓝牙写入、底层实际写片段、通知和 MTU 回调记录 JSON。脚本不主动连接或发送，保留原调用；需要另行准备可用的 Frida 测试环境，**本次没有安装或运行 Frida，也未验证该脚本在手机上的 hook**。

建议抓取一段明确操作顺序的数据：连接 → 握手 → 状态 → 调音量 → 一个方向 → 松开 → 查询关节 → 断开。记录每次 UI 操作时间，即可把静态分析映射到真实帧。优先用读取/状态流程核对协议，再逐项验证动作。

二次开发可直接复用已确认的分层：BLE 串行队列 → 帧流解析 → 命令派发 → 业务状态机。参考代码仅实现离线协议层；完整蓝牙客户端、所有动作载荷和实机兼容性尚未实现或验证。
