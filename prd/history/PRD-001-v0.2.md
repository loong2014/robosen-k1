## 3. 用户流程与验收目标

已确定的两条主流程：

1. 手机搜索目标机器人 → 连接达到业务可用状态 → 在控制页面操作 → K1AI 实机执行相应运动。
2. 编辑积木程序 → 生成动作文件 → 通过 BLE 上传 → 触发机器人执行 → K1AI 实机行为与程序内容一致。

工程创建、保存、重开和兼容的详细流程待明确。手掰编程仍保留在原始需求范围记录中，首版安排待确认。具体控制动作、程序样例、停止条件和量化指标将在细化时定义，不能自行编造为已批准验收门槛。

## 4. 现有证据与技术限制

当前仓库主要包含原 Android/Unity APK 及分析产物，尚无 Flutter 工程。

| 领域 | 已有证据 | 未验证部分 |
|---|---|---|
| BLE 接入 | K1/K1AI 名称前缀、FFE0/FFE1、连接订阅及握手路径 | 实机广播/GATT、固件差异、MTU、握手结果 |
| 基本控制 | 旧协议帧、方向和停止发送路径 | 实际运动含义、控制节奏、异常停止表现 |
| 积木编程 | 数据结构及编辑、生成、上传、播放路径 | 完整积木语义、`.sh` 字节格式、播放载荷 |
| 手掰编程 | 24 个逻辑关节、24 字节姿态采样及多帧保存路径 | 锁定位序/极性、物理映射和时间参数 |
| 动作上传 | 创建文件 `0xDC`、65 字节业务块 `0xE3`、等待 ACK | 路径约束、重试边界、播放完成条件 |

来源：[蓝牙协议分析](../../analysis/reports/蓝牙协议分析.md)、[编程参考报告](../../analysis/reports/图形化与手掰编程复刻参考报告.md)。静态分析和离线验证不等于实机验证。

编程执行的关键阻塞项是 `.sh` 编码规则、`0x17` 播放载荷/完成条件和上传行为。手掰若纳入首版，还需补齐 `0xED` 锁定控制和 `0xE9` 物理关节映射。断线后机器人如何停止也需实测，不能以手机停止发送作为机器人停止的证明。
