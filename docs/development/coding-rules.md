# 通用 AI Coding 规则

适用范围：本项目及后续新建的应用工程。本文由用户“帮我完善补充，通用的规则”的要求建立，与 [需求变更流程](../../prd/WORKFLOW.md) 一起执行。项目特殊约束由已批准的 PRD、技术方案补充。

## 1. 权限与依据

- 开工前阅读根目录 `AGENTS.md`、需求索引、本规则和相关技术文档，核对任务引用的版本及批准范围。
- 新功能、行为变更、验收标准变化走需求变更流程。已有明确批准不重复询问；AI 不得把自己的建议、默认值或用户未回复解释为批准。
- 已授权任务内的局部实现选择、符合既有技术方案的缺陷修复、必要测试和文档同步可自主完成。架构替换、关键依赖变更、跨模块接口或持久化格式变更先进行影响分析。
- 技术变更没有改变产品约束时记录技术决策；改变产品行为、范围、兼容性或验收标准时，同时走 PRD 变更流程。技术批准不能代替产品批准。

## 2. 每项任务的输入与范围

- 记录任务 ID、关联需求及版本、目标、纳入/排除范围、依赖、验收标准、适用测试和交付内容。
- 使用 [编码前检查清单](coding-readiness.md) 判断当前任务是否可开始。前置条件按任务核查，不要求无关功能先全部设计完成。
- 未知协议、第三方能力或性能风险可拆成有边界的调查/验证任务，记录目的、输入、实验范围和退出条件。调查批准不自动授权功能上线。
- 先检查现有代码与工作区变更，复用适合的已有实现。不覆盖其他工作的修改，不顺手扩展范围；发现额外问题单独登记。

## 3. 技术方案与依赖

- 选型前核对官方文档、目标平台支持、许可证、维护情况和已知限制；记录来源及核对日期。不得凭记忆编造“最新版本”。
- 在工具链配置、依赖声明与锁文件中固定可复现的版本；依赖说明见 [清单](../technical/dependencies.md)。文档与实际配置矛盾时先查明原因，不以改文档掩盖意外升级。
- 新增依赖须说明用途、为何现有实现不足、平台/构建影响和验证方式。避免为小功能引入大框架，禁止未经任务授权的批量升级。
- 关键选型使用技术决策记录；普通库选型可写在任务中。已经批准的选型和版本范围内，安装或锁定依赖不需要重复批准。

## 4. 接口、数据和错误处理

- 明确模块职责、输入输出、状态、错误、超时、取消和资源释放；跨模块修改同步所有调用方与对应文档。
- 保持已批准的外部接口和文件格式兼容。格式变更记录版本、旧数据处理、迁移和失败恢复；避免损坏或静默丢弃用户数据。
- 重试前判断是否会产生重复副作用。不得对付款、设备动作、文件写入等操作默认无限重试；没有幂等或确认依据时应返回可解释的失败。
- 区分操作请求已发送、对方已接收和业务执行完成。失败信息应能定位问题，日志避免包含密钥和不必要的个人数据。

## 5. 实现与用户体验

- 优先最小可维护实现，沿用项目风格；不预建未批准的扩展框架，不用临时 mock、固定成功返回或占位数据冒充正式能力。
- 原型、模拟器和测试替身明确标记，并通过配置与真实运行区分；交付时说明其覆盖范围。
- 页面实现覆盖适用的加载、空内容、权限不足、错误、断线、运行中和取消状态；不得用“完成”展示尚未完成的异步操作。
- 状态机、数据规则和协议编解码应可独立测试，不把核心业务逻辑隐藏在 UI 事件中。

## 6. 测试与质量门槛

- 修改前记录相关测试和构建的既有状态；已有失败与本次引入的失败分开报告。
- 根据改动风险运行适用的格式、静态分析、单元、集成及端到端检查。检查命令来自当前项目配置，未配置时先说明，不伪造执行结果。
- 缺陷修复在适用时增加能复现缺陷的回归测试；测试验证预期行为，不只重复实现逻辑。纯文案或低风险可逆调整不强行新增自动化测试。
- 不通过删除断言、跳过测试、放宽阈值或改变验收标准来掩盖失败；确需调整时说明依据并走相应变更流程。
- 记录实际执行命令、环境、结果和证据。未运行、受阻、失败与通过分别标记。测试充分覆盖当前风险后停止无目的重复测试。

## 7. 工作区、配置与交付

- 保留用户未提交修改。清理、回滚或覆盖操作先检查影响，避免使用会丢失无关工作的命令。
- 密钥通过环境或平台安全存储传入，不写入源码、测试样例和日志；提供无真实密钥的配置示例。
- 生成文件说明生成命令及源文件；按项目约定纳入版本控制，不手工修改应由工具生成的内容。应用锁文件应进入版本控制。
- Git 操作遵循用户授权和仓库约定；使用 `codex/` 分支前缀。未收到提交、推送、合并或发布授权时，代码修改不自动扩展为这些操作；已有授权不重复索取。
- 构建和发布记录版本、环境、产物及恢复方式。发布、数据库迁移和固件操作按各自已批准范围执行。

## 8. 变更与完成记录

- 出现新需求冲突、无法满足的技术约束或范围扩大时，记录发现并暂停受影响实现；继续已授权且独立的部分。
- 完成时回看实际 diff，排查无关文件、临时调试内容、配置泄露和文档遗漏。
- 交付提供：关联需求/任务、行为变化、测试证据、剩余问题及限制；不能把“代码已写”或“构建通过”直接等同于业务验收通过。
- 文档同步在同一次任务内完成：PRD 解释行为，技术文档解释方案，任务记录实现，测试记录验证。文档范围不得超过相应批准范围。

## 9. 本项目附加约束

- 实时控制与上传后执行按原 APK 的可验证行为校准。原应用只作为用户指定范围内的参考，不自动扩展为全量复刻要求。
- 实机操作前明确设备型号、固件、操作效果和已验证的停止/退出方式，并在已授权测试范围内执行。未知命令或关节边界先用静态证据、离线向量和原应用记录核对。
- 断线后不能靠手机继续发命令保证机器人停止。机器人端停止行为需实测；禁止重连后自动补发过期运动指令。
- K1 与 K1AI 分开记录兼容证据。K1AI 验收通过不代表 K1 实机已验证；K1 仍保留在产品支持目标内，缺少实机时如实标注验证缺口。

本文是 AI 工作约定。将来 CI 可校验文档关联、构建和测试，但不能自动证明语义无冲突或替代用户批准。
