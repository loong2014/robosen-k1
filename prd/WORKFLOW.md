# 需求与变更处理流程

## 1. 输入分类

| 输入 | 处理路径 | 代码修改条件 |
|---|---|---|
| 初始 PRD 定版、新功能、行为或验收标准变化 | 完整变更记录和用户批准 | 通过下述开发门槛 |
| 缺陷修复 | 关联已批准需求，记录实际与预期差异、影响和回归验证 | 已有修复授权且确实恢复原需求；改变预期则转完整变更 |
| 内部重构、依赖维护 | 记录行为不变依据及影响 | 已获相应工作授权，且不改变已批准约束；否则转完整变更 |
| 澄清、只读分析、文档排错 | 直接完成并标明状态 | 不产生功能实施授权，不改变已批准含义 |

后三类的记录可以放在现有任务或关联 CR 内，无须为每个小修改新增文档。对分类有疑问时，先查需求和代码；确实影响产品行为或兼容性则走完整变更。

## 2. 完整变更步骤

1. **登记**：使用 `templates/CHANGE.md` 创建 `changes/CR-NNN-主题.md`。写明用户原始诉求、目标、相关需求 ID、当前基线版本和拟议差异。初始定版的旧基线填“无”。
2. **冲突检查**：检查相关已批准 PRD、跨模块约束、待审变更、技术设计和实际代码。逐项写明“无冲突 / 冲突 / 信息不足”与依据，不能只写“已检查”。
3. **影响分析**：列出受影响功能、接口、数据、兼容性、开发任务、测试和风险。现有代码与 PRD 不一致时单独记录偏差，不能以代码为理由悄悄改需求。
4. **提出可审阅方案**：给出新旧行为对照、处理选项、推荐方案、验收标准和所需验证。发生冲突时明确保留、替代、拆分到以后或拒绝的具体需求。
5. **决定**：用户明确批准具体版本和范围后记录批准；若用户已在当前会话明确批准该具体方案，直接记录并继续。仅提出想法、沉默、AI 建议或“没有冲突”均不构成批准。
6. **同步基线**：保存可追溯旧版本，再更新 PRD 版本、变更历史和索引；关联被替代需求。同步技术方案、计划和测试用例，避免多份文档互相矛盾。
7. **实施与验证**：仅实施批准范围。将结果和证据写回任务/CR。测试未通过、缺少目标设备或未完成实机验证时如实标记，不改写为验收通过。

部分批准时，必须列出批准和未批准的需求 ID；索引只把批准部分列入有效基线。实施途中出现未批准的扩大范围，新增或修订 CR，保留原决定，重新处理受影响内容。

## 3. 必查的冲突和影响

- **范围与行为**：功能是否互斥，操作语义是否改变，是否增加原来明确排除的能力。
- **设备与平台**：目标型号、固件、Android/iOS 范围是否变化。
- **BLE 与执行**：命令格式、连接状态、ACK、超时、并发、动作执行方式是否兼容。
- **机器人状态**：运动停止、关节锁定、编程运行与手动控制的关系是否变化。
- **数据与兼容**：工程格式、迁移、已有动作、导入导出是否受影响。
- **质量与验收**：成功率、延迟、离线能力、异常处理及已通过测试是否受影响。
- **交付依赖**：是否依赖未确认协议、实机条件或未完成的其他变更。

不适用的项写明原因。信息不足的关键项不能当作“无冲突”通过；可以先批准范围清楚的调查任务，调查批准不自动授权产品实施。

## 4. 状态与批准证据

审批状态：`draft` → `in_review` → `approved` 或 `rejected`；被新版本完整替代后标为 `superseded`。审批后的提案内容不得无记录地重写。

交付状态独立记录：`not_started`、`in_progress`、`blocked`、`implemented`、`verified`。其中 `verified` 要有对应验收用例和结果；仅合并代码或自动化测试通过不一定足够。

批准记录包含：日期、批准人（用户）、明确批准的版本/需求 ID、条件、决定原文或会话定位。没有定位链接时记录日期及准确原文，不编造链接或批准。用户选定替代行为后，记录其覆盖的旧需求及原因。

已批准文档更新前，确保旧版本可从 Git 提交恢复并记录提交 ID；若尚未进入 Git，则保存到 `prd/history/` 并在变更记录中引用。草案改进不要求每次存一份快照。

## 5. 开发与完成门槛

开始产品代码修改前，确认：

- 相关需求已批准，验收标准明确，无未解决的关键冲突。
- 适用技术方案已经确认；开发任务与需求 ID 对应。
- 对应测试用例已定义，包括必要的异常场景和实机条件。
- 协议等阻塞项已解决，或当前任务明确限定为获批的调查/验证工作。

完成时提供需求 ID、实际改动、测试结果、证据路径和剩余限制。涉及目标设备上的机器人动作，以实机结果作为最终验收依据。

本流程当前通过 `AGENTS.md` 约束 AI 行为。未来的 CI 可以检查编号、状态、文档关联和必要测试，语义冲突判断和批准仍需审阅。

## 6. 技术变更与开工判断

技术方案、主要依赖及版本遵守 [技术文档规范](../docs/technical/README.md)。不改变产品约束的关键技术选择记录 ADR；涉及产品范围、行为、数据兼容承诺或验收标准的变化，同时关联 CR。

通用实施规则见 [coding-rules.md](../docs/development/coding-rules.md)，每项任务使用 [coding-readiness.md](../docs/development/coding-readiness.md) 检查前置条件。门槛按任务及其依赖判断，不以整个项目尚有未决项为由阻断已获授权的独立工作。

PRD 整体为 draft 时，可以有明确标记的 approved 条款；索引和 CR 必须列出具体 ID。批准这些条款不自动批准尚未定义的实现细节，也不将全部验收条件视为已满足。
