## 环境和样例

离线用例使用仓库原生 codec 对照向量及其边界派生输入。Flutter UI/文件测试使用明确标记的测试替身。所有真机用例分别在 Android、iOS 手机与用户 K1AI 上运行，记录系统、固件、应用版本；K1 无实机时标 not_run，不继承 K1AI 通过结果。

动作样例由 T06 从原 APK 和原生代码建立：F1 一个已验证动作，F2 两个可区分的顺序动作，F3 将 F2 子序列重复两次，以观察循环的实际次数。具体关节和参数要有设备证据后才能写入样本；这些占位样例尚不可直接用于机器人执行。

| ID / 关联需求 | 前置与输入 | 步骤 | 预期结果与证据 |
|---|---|---|---|
| TC-BUILD-01 / REQ-PLT-001 | T01 工程、候选工具链 | 解析锁文件，格式/分析/测试，构建 Android debug 和 iOS 无签名产物 | 检查通过；记录实际版本和命令。iOS 真机安装另需签名，构建不算 BLE 验收 |
| TC-PROTO-01 / REQ-BLE-001 | 96 组原生机器码对照 | Dart 编码每组命令与载荷，逐字节比较 | 与原生向量一致；不能仅对 Dart 自己解码来证明编码正确 |
| TC-PROTO-02 / REQ-BLE-001 | 合法帧、拆分/合并、前导噪声、坏校验 | 对多种切片逐次 feed，再输入正常帧 | 合法帧只产出一次；坏帧不派发；重同步和顺序符合规格 |
| TC-PROTO-03 / REQ-BLE-001 | 253/254 字节、非法命令、断线半帧、短状态 | 编码边界并清空会话后继续解析 | 合法上限成功、超限拒绝、旧半帧不跨会话拼接、短状态按规格处理 |
| TC-BLE-01 / REQ-BLE-001 | 权限未授予、蓝牙关闭 | 进入扫描，分别拒绝/允许权限、切换蓝牙 | 显示准确状态、无崩溃、不绕过权限；可由用户恢复扫描 |
| TC-BLE-02 / REQ-DEV-001、REQ-BLE-001 | K1AI 实机，适用时补测 K1 | 扫描、选定设备、发现服务、订阅、握手 | 目标设备可见；日志证明正确服务、握手成功后才 ready |
| TC-BLE-03 / REQ-BLE-001 | 模拟错误服务、订阅错误、握手失败 | 逐个注入故障并重试 | 不显示 ready、不发运动；错误可解释，旧订阅被清理 |
| TC-BLE-04 / REQ-BLE-001 | 会话有待处理请求 | 断线并重新连接，注入旧回调/旧 ACK | 旧请求失败并清队列；旧会话事件不修改新状态；不重播旧运动 |

| TC-CTL-02 / REQ-CTL-001 | 方向持续输入 | 指针取消、切页、切后台、断线、重新连接 | 方向定时器/队列终止；链路可用时尝试停止；重连不自动运动；实机停止表现单独记录 |
| TC-EDIT-01 / REQ-VIS-001、REQ-UX-001 | 无 BLE；起始、动作、循环、动作子积木、两种单条指令 | 从积木区拖入自由画布，移动、连接/断开、改参数、调整顺序、删除、撤销/重做 | 候选连接可见；显式连接和执行顺序一致；位置变化不错误改变语义；非法连接不丢积木 |
| TC-EDIT-02 / REQ-COMP-001 | 含中文名称、动作参数和循环的工程 | 保存、终止应用、重开并编译动作计划 | 节点 ID、参数、连接顺序及显示位置保留；计划与保存前一致 |
| TC-EDIT-03 / REQ-COMP-001 | 保存中断、损坏文件、未知 schema、非法节点引用 | 注入故障后读取/校验 | 不覆盖最后有效工程，不静默丢内容；明确拒绝损坏/未知格式与无效程序 |
| TC-EDIT-04 / REQ-UX-001、REQ-COMP-001 | 原应用操作录屏、Android/iOS 普通手机、旧 v1 工程 | 对照新增、拖动、吸附、断开、参数、删除；重开旧工程并检查视口 | 逐项记录原版差异；两平台触摸操作可用，无积木遮挡/误触致数据丢失；旧工程迁移无损。缺原版录屏时不判原版操作等同 |
| TC-EVID-01 / REQ-VIS-002 | 原 APK + T06 样例或可靠原生字节证据 | 对 F1/F2/F3 及一次参数变化做对照 | 记录字段含义、字节和行为；无法解释的部分保持未验证，阻塞对应执行 |
| TC-RUN-01 / REQ-VIS-001、REQ-VIS-002 | 已验证 schema、动作规格和样例 | 将对应积木编译，与样本对照 | 字节匹配，或每项差异有格式依据；行为匹配不能只凭上传成功推定 |
| TC-RUN-02 / REQ-VIS-002 | 已知文件、不同模拟 MTU、65 字节业务块 | 上传并注入正确 ACK，记录每片 | 业务块与 ATT 分片正确；ACK 前不发下一业务块；最终字节与源一致 |
| TC-RUN-03 / REQ-VIS-002 | 正在上传或等待播放确认 | 注入 ACK 超时/重复/迟到、断线、取消 | 不跳块、不盲目重写不确定块、不自动播放；迟到同码 ACK 不被错误计入新上传；状态明确失败或未知 |
| TC-RUN-04 / REQ-VIS-002、REQ-ACC-001 | K1AI + F1/F2/F3 对应工程 | 上传、执行、观察顺序和循环次数 | K1AI 按程序执行；完成提示有真实依据；记录手机日志及机器人行为 |
| TC-E2E-01 / REQ-ACC-001、REQ-PLT-001、REQ-COMP-001 | Android/iOS 分别安装，K1AI、已验证程序 | 扫描连接→实时控制→保存重开工程→上传执行 | 两平台分别完成闭环，无模拟数据冒充成功；问题和未覆盖设备单列 |

## 执行记录和清理

每次执行生成记录：用例 ID、代码/应用版本、环境、操作者、输入样例路径、步骤、实际结果、证据、状态。清理时取消测试定时器、释放连接和订阅；仅在已确认停止流程下结束实机运动。测试工程使用独立名称，不覆盖用户工程或原 APK 文件。

超时、发送频率和性能测量先记录实测值，在相应协议/体验规格确定后转为阈值断言，不填写无依据的“连接 100% 成功”等指标。
